# Subscription Starter

Базовый fullstack-проект магазина цифровых продуктов с подписками. Frontend написан на HTML, SCSS и обычном JavaScript с Vite; backend — Node.js и Express 5; данные хранятся в PostgreSQL через Prisma 6. Интерфейс намеренно простой: страницы, формы и таблицы можно заменить своим дизайном, сохранив API.

Реализованы регистрация, серверные сессии, восстановление пароля, личный кабинет, каталог, тарифы, заказы, промокоды, подписки и административные разделы. Оплата работает в **локальном sandbox-режиме**: деньги не списываются, платёж подтверждается подписанным webhook из серверной CLI-команды. Готового подключения к банку или платёжному агрегатору нет.

## Быстрый запуск

Потребуются Node.js **22.12 или новее**, npm и PostgreSQL. Для запуска базы из комплекта установите Docker с Docker Compose. Все команды ниже выполняются из корня `subscription-starter`.

```sh
npm install
npm run setup:env
docker compose up -d db
```

`setup:env` создаёт `server/.env` из примера и генерирует случайные `PAYMENT_WEBHOOK_SECRET` и `SEED_ADMIN_PASSWORD`. Существующий `.env` сохраняется. Не заменяйте эти значения строками-заглушками из `.env.example`.

Дождитесь состояния `healthy` у базы:

```sh
docker compose ps
```

Затем подготовьте Prisma и демонстрационные данные:

```sh
npm run db:generate
npm run db:migrate
npm run db:seed
npm run dev
```

- Сайт: <http://localhost:5173>.
- Backend: <http://localhost:3000>.
- Проверка подключения к БД: <http://localhost:3000/api/health>.
- Административная панель: <http://localhost:5173/admin>.

Email тестового администратора — значение `SEED_ADMIN_EMAIL`, по умолчанию `admin@example.test`. **Пароль находится в `SEED_ADMIN_PASSWORD` внутри вашего `server/.env`**; общего пароля в исходниках нет. Вход выполняется через обычную страницу авторизации. Seed создаёт три продукта, по четыре тарифа на каждый продукт и промокоды `WELCOME10` / `SAVE100`.

Seed сохраняет существующие записи. Изменение `SEED_ADMIN_PASSWORD` после первого запуска seed не меняет пароль уже созданного пользователя; используйте восстановление пароля или профиль. Демонстрационный seed отключён при `NODE_ENV=production`.

При использовании собственной PostgreSQL укажите её URL в `server/.env` и пропустите команду Docker. По умолчанию контейнер публикует порт 5432 только на `127.0.0.1`; его пароль предназначен для локальной разработки. Если этот порт занят, измените сопоставление порта в `docker-compose.yml` и соответствующий порт в `DATABASE_URL`.

## Проверка покупки

1. Зарегистрируйтесь или войдите в аккаунт, откройте каталог и выберите тариф.
2. При желании примените `WELCOME10` или `SAVE100`, затем создайте заказ. Сервер заново проверит цену и доступность промокода.
3. Скопируйте UUID созданного заказа. До подтверждения оплаты заказ остаётся `pending`, подписка не выдаётся.
4. Пока backend запущен, выполните в другом терминале:

```sh
npm run sandbox:pay -- "UUID_ЗАКАЗА"
```

5. Обновите заказ и страницу подписок: заказ станет `paid`, платёж — `succeeded`, подписка — `active`.
6. Создайте и оплатите второй заказ того же продукта: действующая подписка продлится от текущей даты окончания.

Повторная отправка подтверждения того же оплаченного заказа возвращает `alreadyProcessed: true` и не выдаёт дополнительный срок. Платёж для отменённого или просроченного заказа отклоняется. Время оплаты заказа ограничено 30 минутами.

CLI читает платёж из вашей базы, подписывает исходные байты JSON секретом из `server/.env` и отправляет webhook на `SERVER_URL`. Команда доступна только на стороне сервера; секрет не передаётся в frontend. Клиентского endpoint «оплата успешна» нет.

## Модель данных и бизнес-правила

| Модель | Назначение |
| --- | --- |
| `User` | Уникальные email и username, bcrypt hash, роль, блокировка, баланс. Поле balance зарезервировано; кошелёк и пополнение не реализованы. |
| `Product` | Продукт, slug, описания, изображение, доступность. |
| `Plan` | Тариф конкретного продукта, цена и длительность в днях. |
| `Subscription` | Одна запись на пару пользователь/продукт, тариф, начало, окончание, статус. |
| `Order` | Заказ и снимок цены, скидки, валюты, длительности; ключ идемпотентности и срок оплаты. |
| `PromoCode` | Процентная или фиксированная скидка, срок, лимит, число использований и резервов. |
| `Payment` | Связь с заказом и провайдером, сумма, валюта, статус. |
| `AdminLog` | Аудит административных изменений с автором и идентификатором сущности. |
| `Session` | SHA-256 hash случайного токена серверной сессии. |
| `PasswordReset` | Hash одноразового токена восстановления со сроком действия. |

Суммы хранятся в `Decimal(12,2)` и возвращаются JSON-строками, валюта — RUB. Время в API передаётся ISO-строками; длительность тарифа — интервалы по 24 часа. Backend не принимает цену, роль пользователя, результат оплаты или длительность подписки от покупателя.

При оформлении сервер проверяет активность продукта и тарифа, принадлежность тарифа продукту и доступность промокода. В заказ записываются снимки суммы и длительности, поэтому последующее изменение тарифа не меняет уже созданный заказ. Клиент отправляет UUID `idempotencyKey`: повтор одного запроса возвращает тот же заказ, а попытка использовать этот ключ с другими данными отклоняется. У пользователя может быть не более десяти неоплаченных заказов одновременно.

Промокоды общие для каталога. Процент не превышает 100; фиксированная скидка ограничена стоимостью тарифа, отрицательной итоговой цены нет. Создание заказа резервирует одно использование; оплата превращает резерв в использование; отмена освобождает резерв. Проверяется сумма `usedCount + reservedCount`, что защищает лимит при параллельных покупках. Уже связанный с заказом текст промокода переименовать нельзя: для нового названия создайте новый код. Можно менять его скидку, доступность, срок и лимит; новые условия применяются к новым заказам.

Обновление заказа, платежа, подписки и счётчиков промокода выполняется в одной serializable-транзакции с ограниченными повторами при конфликтах. Существующая действующая подписка продлевается от её окончания. Истёкшая или отменённая начинается заново с момента оплаты. Уникальная пара `userId + productId` предотвращает появление конфликтующих подписок.

Backend раз в минуту обрабатывает просроченные заказы, статусы подписок, истёкшие сессии и токены восстановления. За один проход отменяется до 100 просроченных заказов; следующие проходы обрабатывают остаток. Обслуживание заказов также запускается при оформлении и проверке промокода. Отдельный ручной запуск:

```sh
npm run orders:expire
```

Статусы заказов: `pending`, `paid`, `cancelled`, `refunded`. Платежей: `pending`, `succeeded`, `cancelled`, `refunded`. Подписок: `active`, `expired`, `cancelled`. **Refund-статусы предусмотрены моделью, но автоматические возвраты через провайдера и интерфейс возвратов пока не реализованы.** Продление требует отдельного заказа: автосписания и рекуррентный биллинг отсутствуют.

## REST API

Префикс всех маршрутов — `/api`. Успех:

```json
{ "success": true, "data": {} }
```

Ошибка:

```json
{ "success": false, "message": "Описание ошибки" }
```

Постраничные списки возвращают `data: { items, total, page, pageSize }`; по умолчанию страница 1 и 20 записей, максимум 100 записей. `/plans` и пользовательский `/subscriptions` возвращают массивы. Неизвестные поля отклоняются валидацией. ID — UUID; денежные поля административных запросов принимают десятичную строку или число с максимум двумя знаками после запятой.

Для изменяющих запросов браузер использует `Content-Type: application/json`, `X-Requested-With: XMLHttpRequest` и `credentials: 'include'`. Допускаются только настроенные origin. Webhook использует собственную подпись и исходное тело запроса вместо cookie/CSRF-заголовка.

### Авторизация и профиль

| Метод и путь | Доступ | Тело / результат |
| --- | --- | --- |
| `POST /auth/register` | Публичный | `{ username, email, password, confirmPassword }`; создаёт пользователя и сессию. |
| `POST /auth/login` | Публичный | `{ email, password }`; устанавливает cookie. |
| `POST /auth/logout` | Пользователь | `{}`; удаляет текущую сессию. |
| `GET /auth/me` | Пользователь | Безопасные поля пользователя. |
| `POST /auth/forgot-password` | Публичный | `{ email }`; одинаковое подтверждение независимо от существования аккаунта. |
| `POST /auth/reset-password` | Публичный | `{ token, password, confirmPassword }`; одноразовый токен. |
| `GET /users/me` | Пользователь | Профиль. |
| `PATCH /users/me` | Пользователь | `{ username, email, currentPassword }`. |
| `PATCH /users/me/password` | Пользователь | `{ currentPassword, password, confirmPassword }`; завершает все сессии. |

Логин нормализуется в нижний регистр, допускает 3–32 латинских символа, цифры и `_`. Email тоже нормализуется. Новый пароль содержит не менее 10 символов и занимает не более 72 байт UTF-8 — ограничение bcrypt. Пароли хешируются с cost 12. Сессия хранится в HttpOnly-cookie, `SameSite=Lax`, а в production также `Secure`; в БД находится только hash случайного токена.

Восстановление действует 30 минут. Без SMTP в development письмо сохраняется локально в `server/storage/mail-outbox/*.json`; откройте его и перейдите по ссылке. Эта папка не раздаётся как статика. Токен не возвращается через API. В production нужен SMTP. Изменение email аннулирует старые ссылки восстановления, изменение/сброс пароля завершает все сессии.

| Метод и путь | Доступ | Параметры / результат |
| --- | --- | --- |
| `GET /products` | Публичный | `page`, `pageSize`; активные продукты с активными тарифами. |
| `GET /products/:slug` | Публичный | Продукт с тарифами. |
| `GET /plans` | Публичный | Необязательный `productId`; массив активных тарифов. |
| `GET /subscriptions` | Пользователь | Только свои подписки с продуктом, тарифом и датой окончания. |
| `POST /orders` | Пользователь | `{ productId, planId, promoCode?, idempotencyKey }`. |
| `GET /orders` | Пользователь | `page`, `pageSize`; только свои заказы. |
| `GET /orders/:id` | Пользователь | Свой заказ; чужой UUID возвращает 404. |

Пример тела оформления заказа:

```json
{
  "productId": "d2106cbe-75ae-40d6-a03f-55df763155d3",
  "planId": "c498cdba-3bce-4e86-819e-62eb682fc22b",
  "promoCode": "WELCOME10",
  "idempotencyKey": "50d9ba1e-6994-438c-ad89-360f5fb27041"
}
```

Используйте реальные ID из `/products` и новый ключ `crypto.randomUUID()` для новой покупки. Для повтора той же операции после сетевой ошибки сохраняйте прежний ключ и тело.

### Административный API

Все маршруты ниже требуют действующую сессию незаблокированного пользователя с ролью `admin`. GET-списки поддерживают `page`, `pageSize`.

| Метод и путь | Поля / действие |
| --- | --- |
| `GET /admin/dashboard` | `users`, `activeSubscriptions`, `orders`, `paidOrders`, `totalRevenue`; выручка суммируется по оплаченным заказам. |
| `GET /admin/users` | Поиск `search` по username/email. |
| `PATCH /admin/users/:id` | `{ isBlocked?, role? }`, роль `user` или `admin`. |
| `GET /admin/products` | Все продукты, включая отключённые. |
| `POST /admin/products` | `{ name, slug, description, shortDescription, image?, isActive? }`. |
| `PATCH /admin/products/:id` | Изменяемые поля продукта. |
| `DELETE /admin/products/:id` | Деактивирует продукт и его тарифы, сохраняет историю покупок. |
| `GET /admin/plans` | Необязательный фильтр `productId`. |
| `POST /admin/plans` | `{ productId, name, durationDays, price, isActive? }`. |
| `PATCH /admin/plans/:id` | Изменяемые поля тарифа; использованный тариф нельзя перенести в другой продукт. |
| `GET /admin/promocodes` | Все промокоды со счётчиками использований и резервов. |
| `POST /admin/promocodes` | `{ code, type, value, maxUses?, expiresAt?, isActive? }`. |
| `PATCH /admin/promocodes/:id` | Изменение/отключение кода; лимит не ниже использований и резервов. |
| `GET /admin/orders` | Фильтры `status`, `userId`, `productId`. |
| `GET /admin/subscriptions` | Фильтры `status`, `userId`, `productId`; учитывается фактическая дата окончания. |
| `POST /admin/subscriptions` | `{ userId, productId, planId, expiresAt }`; ручная выдача или продление. |
| `PATCH /admin/subscriptions/:id` | `{ expiresAt?, status? }`; изменение срока или отмена. |
| `GET /admin/payments` | Необязательный фильтр `status`. |
| `GET /admin/logs` | Административный журнал. |

В PATCH требуется хотя бы одно поле. `image` может быть `null`, URL http(s) или локальным путём `/...`; пустая строка становится `null`. `maxUses: null` означает отсутствие общего лимита; `expiresAt: null` у промокода — отсутствие срока. `type` промокода — `percent` или `fixed`, `value` — положительная сумма/процент. При отключении продукта через DELETE тарифы отключаются отдельно; повторное включение продукта не включает их автоматически.

Ручная подписка требует будущего `expiresAt` в ISO-формате и тарифа выбранного продукта. Она не создаёт фиктивный оплаченный заказ. Если активная подписка уже существует, новая дата должна быть позже текущей; сократить срок можно через PATCH. Установка будущей даты для истёкшей подписки активирует её; для отменённой нужно явно передать `status: "active"`. Статус `active` требует будущую дату, `expired` — прошедшую, `cancelled` отменяет доступ независимо от даты.

Нельзя заблокировать себя, снять свою административную роль или отключить последнего активного администратора. Блокировка аннулирует сессии и reset-токены, изменение роли — сессии. Права повторно проверяются внутри транзакции изменения. Каждое изменение администратором и запись его аудита фиксируются вместе; пароли, токены и произвольные исходные тела запросов в журнал не записываются.

## Платёжный адаптер

Граница провайдера находится в `server/services/payment-provider.js`, обработка состояния — в `server/services/payments.js`:

```text
Frontend → POST /orders → Order + Payment → провайдер
Провайдер → подписанный webhook → проверка → транзакция → подписка
```

Контракт адаптера содержит `createPayment()`, `checkPayment()` и `handleWebhook()`. Sandbox не делает сетевых запросов при создании платежа, возвращает `checkoutUrl: null` и использует локальную запись для проверки статуса.

Sandbox-подпись — HMAC-SHA256 над `timestamp + "." + rawBody`. Заголовок имеет вид `timestamp.hex_signature`, допустимое отклонение времени — пять минут; сравнение подписи выполняется через `timingSafeEqual`. Проверяются схема события, статус `succeeded`, идентификаторы заказа/платежа, провайдер, обе сохранённые суммы и валюта, текущие статусы и срок оплаты. Повторные подтверждения не продлевают подписку повторно.

Для подключения настоящего провайдера необходимо:

1. Реализовать его API и проверку **реальной** подписи webhook по исходным байтам согласно документации провайдера; секреты остаются в серверном окружении. Адаптер должен проверять серверное подтверждение и возвращать доверенное нормализованное событие.
2. Вынести сетевое создание платежа из повторяемой БД-транзакции в transactional outbox и worker. Сохранить намерение создать платёж вместе с заказом, использовать `order.id` как ключ идемпотентности провайдера, повторять доставку безопасно и сохранять результат. У текущего sandbox нет внешних побочных эффектов, поэтому его создание допустимо внутри транзакции.
3. Добавить сверку платежей с API провайдера, обработку задержанных webhook, журнал входящих событий и политику для оплаты после отмены/таймаута. В текущем sandbox такой webhook отклоняется; реальные списанные деньги требуют сверки и, при необходимости, возврата.
4. Реализовать отмену у провайдера, возвраты, обработку ошибок и бизнес-правила отзыва доступа. Одних полей `refunded` недостаточно для реального возврата.
5. Добавить и протестировать настройку нового адаптера в `config/env.js`. Сейчас допускается только `PAYMENT_PROVIDER=sandbox`, и запуск sandbox в `NODE_ENV=production` намеренно запрещён.

## Выдача цифрового продукта

Проект управляет правом доступа, но не содержит ваши файлы, уроки или внешний сервис продукта. Для будущего endpoint скачивания/контента уже есть `requireProductAccess(userId, productId)` в `server/services/catalog.js`.

После `requireAuth` вызовите этот сервис с `req.user.id` и проверенным ID продукта. Он проверяет пользователя, активность продукта, статус подписки и `expiresAt > now`. Затем сервер может сформировать короткую подписанную ссылку на приватное хранилище или передать разрешённый контент. Не размещайте платные файлы в публичном `client/public`, не полагайтесь на скрытую кнопку frontend и не проверяйте только сохранённую строку `status`.

| Переменная | Назначение |
| --- | --- |

| `PAYMENT_PROVIDER` | Сейчас только `sandbox`. |
| `PAYMENT_API_KEY` | Место для ключа будущего провайдера; sandbox его не использует. |
| `PAYMENT_WEBHOOK_SECRET` | Секрет подписи sandbox, минимум 32 символа. |

Файлы `.env`, локальная почта, сборка и `node_modules` исключены из Git. Frontend не нуждается в ключах; всё, помещённое в клиентскую сборку, считается публичным. При смене порта API обновите `PORT`, `SERVER_URL` и proxy target в `client/vite.config.js`.

## Сборка, проверки и дальнейшее развёртывание

```sh
npm run build
npm test
```

`build` создаёт `client/dist`. Express автоматически раздаёт эту сборку и поддерживает SPA-маршруты, если папка существует. Для локальной проверки собранного приложения остановите dev-процессы, установите `CLIENT_URL=http://localhost:3000` в `.env`, выполните `npm start` и откройте порт 3000. В этом локальном сценарии оставьте `NODE_ENV=development`; изменение на production потребует готового платёжного адаптера.

Интеграционные тесты требуют отдельной PostgreSQL для тестов; не запускайте их против рабочей базы. Точная настройка и состав проверок указаны в тестовых файлах проекта. Изменение схемы при разработке оформляйте отдельной миграцией через `npm run db:dev -w server -- --name имя_миграции`; имеющиеся миграции применяются `npm run db:migrate`.

Перед реальным запуском настройте HTTPS, production cookie, корректные разрешённые origin и доверенные reverse proxy, SMTP, отдельные секреты и учётные данные БД, резервное копирование и мониторинг. Удобная схема — frontend и `/api` на одном origin. Не открывайте PostgreSQL публично и не используйте локальные демонстрационные пароли.

Текущие rate limiter используют память одного процесса. Для нескольких экземпляров backend нужен общий store, например Redis, и корректная обработка IP за proxy. Периодическое обслуживание и платёжный outbox следует вынести в отдельные управляемые worker-задачи. Дополнительно подготовьте проверки авторизации защищённого контента, идемпотентности и отказов реального провайдера, а также процессы возвратов и работы с обращениями пользователей.

## Если что-то не запускается

- `Invalid environment` — сначала выполните `npm run setup:env` и проверьте `server/.env`.
- Prisma сообщает, что клиент не создан, — выполните `npm run db:generate` после установки зависимостей/изменения схемы.
- Соединение с БД недоступно — проверьте `docker compose ps`, порт и `DATABASE_URL`; затем примените миграции.
- На API получен 403 при ручном POST/PATCH/DELETE — проверьте cookie, origin и `X-Requested-With: XMLHttpRequest`; frontend выставляет их сам.
- Сессия не работает после изменения роли/пароля — войдите заново; предыдущие сессии аннулируются специально.
- Письмо восстановления не пришло в development — без SMTP оно находится в `server/storage/mail-outbox`.
- Sandbox webhook вернул 409 — заказ уже отменён или истекли 30 минут; создайте новый заказ.
- Production не стартует с sandbox — требуется реализовать и включить настоящий платёжный адаптер, как описано выше.
