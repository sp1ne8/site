# Работа с юридическим модулем HYDRA

Все исходные документы — проекты. Не выставляйте проверку или реальные реквизиты фиктивно, чтобы обойти публикационные ограничения.

## Локальный запуск и обновление

Из папки subscription-starter, после остановки текущего npm run dev (Ctrl+C):

```powershell
npm install
npm run db:generate
npm run db:migrate
npm run dev
```

При старте backend создаёт недостающие проекты RU/KZ/BY/OTHER_CIS idempotent upsert. Уже существующие тексты, настройки, товары и тарифы не переписываются. Работающий Node на Windows может удерживать Prisma DLL — остановите dev перед db:generate.

Юридические страницы доступны без входа: /privacy-policy, /personal-data-policy, /user-consent, /cookie-policy, /terms, /offer, /refund-policy, /marketing-consent. Выбор версии страны — ?jurisdiction=RU/KZ/BY/OTHER_CIS. Ссылка с ?document=<UUID> открывает конкретную сохранённую версию.

Аккаунт: /privacy-data или «Privacy & Data» в меню имени пользователя. Admin: /admin/legal или «Legal / Privacy» в админке. Вход — обычные admin-учётные данные из реально созданной БД, а не автоматическое изменение аккаунта при редактировании .env.

Существующим аккаунтам без страны предложено выбрать юридическую конфигурацию в Privacy & Data. До этого новый checkout блокируется сервером. Для договорной RU/BY-модели ознакомление с политикой не называется согласием на все данные. Для KZ по умолчанию отдельное согласие; его применимость должен утвердить специалист.

## Настройка и публикация

1. Jurisdictions → нужная страна → заполните реальные реквизиты, размещение/получателей, основания, сроки и правила. На этом этапе enabled оставьте выключенным. Изменение revision делает предыдущий optional-выбор неактуальным.
2. Разные сроки прав не сводите к одному числу requestDays: это календарный fallback для интерфейса. Зафиксируйте обязательные сроки/формы по типам в requestProcedure, назначайте соответствующую dueAt вручную и обеспечьте контроль вне интерфейса.
3. Проверенные HTTPS origins внешних картинок перечислите в externalMediaOrigins. Проверяйте страну, технические логи/cookies получателя и основание передачи. Production не разрешает Third-party, если хоть один активный источник не проверен. Изменение набора origin требует нового cookie-выбора.
4. Documents → новая версия/копия проекта → заполните текст; обычный текст, заголовки ##, HTML не исполняется. Сохраните, затем подтвердите юридическую проверку и опубликуйте. При публикации прежняя версия становится архивной. Placeholders запрещены.
5. Если проект уже использован в подтверждении, его нельзя переписать: создайте новую версию. Для свободных проектов история правок хранится в защищённом журнале before/after; кнопка «История». Старые подтверждения всегда ссылаются на сохранённую версию.
6. После публикации семи основных документов включите проверенную юрисдикцию. Маркетинг в этой сборке отсутствует; новый marketing opt-in выключен и не обязателен. Его нельзя активировать просто изменением текста политики.
7. OTHER_CIS не включается галочкой. Для новой страны добавьте проверенный code/settings/flow/documents и тесты. Выбор страны не доказывает гражданство/применимое право и не меняет размещение БД.

Проверка специалиста — реальная организационная работа, а не техническая возможность поставить checkbox. Нельзя обходить ограничения непосредственными SQL-update в production.

## Cookies и новые сервисы

- sid: имя из COOKIE_NAME, TTL из SESSION_TTL_DAYS; вход/безопасность, HttpOnly/SameSite=Lax, Secure в production.
- hydra_privacy: session cookie, создаётся только после выбора; хранит случайный ID решения, hash в БД. Это не рекламный ID. Browser restore может сохранять session cookies в зависимости от браузера.
- checkout:* — sessionStorage вкладки для идемпотентности заказа.
- Preferences/Analytics/Marketing SDK сейчас отсутствуют. Не создавайте фиктивные cookies в политике.
- Сторонние изображения в каталоге и admin-карточках имеют src только после Third-party grant. Источник неактивного продукта вне реестра активного каталога не загружается. Отзыв убирает внешние изображения и прекращает новые загрузки, но не отменяет уже произошедшую передачу и не удаляет cookie чужого домена.
- Новый SDK подключается через optionalTechnology boundary только после отдельного аудита, соответствующей backend availability, документа/версии и consent purpose. Он должен возвращать cleanup, прекращающий новые отправки и удаляющий свои first-party identifiers. Не вставляйте script в index.html до выбора.
- Дополнительный сервис подтверждения KZ регистрируется backend-функцией registerConsentVerifier. Проверяйте субъекта, цель и documentId по доверенному каналу; храните внешнее доказательство по утверждённым правилам. Не доверяйте frontend token сам по себе.

## Обращения и закрытие аккаунта

- Data Requests показывает тип, владельца, статус, срок и ответ. Необходимо организационно контролировать сроки и корректность ответа. Внешнее обращение по email/адресу сохраняет силу; блокированный пользователь не обязан входить в кабинет.
- Удаление в кабинете — запрос с подтверждением текущего пароля. Для обращений вне кабинета установите соразмерную проверку личности без лишнего сбора документов.
- Проверьте действующие обязательства, доступ, споры, обязательный учёт, основание и конечную дату сохраняемых записей.
- Отдельное admin-действие закрывает аккаунт, отменяет pending orders и активный доступ, отзывает сеансы/reset, убирает действующие email/username/passwordHash. Создаётся RetentionHold с составом, основанием и reviewAt. Бывший admin сначала передаёт обязанности и теряет роль; нельзя закрыть себя.
- Ответ после закрытия доступен admin; до прекращения входа согласуйте с пользователем реальный канал получения ответа. Текущий модуль не рассылает его автоматически и не сохраняет исходный email после псевдонимизации.
- Это не полное физическое удаление/анонимизация: UUID и связи с заказами/согласиями/обращениями остаются. Записи нельзя использовать для рассылки, нового входа или реактивации через обычный admin update.
- ReviewAt — сигнал пересмотра, а не автоматическое разрешение уничтожить финансовые записи. По окончании основания оператор выполняет проверенную процедуру уничтожения в БД/провайдерских копиях/backup и фиксирует результат. Автоматического financial purge в проекте нет.

Retention dry run:

```powershell
npm run privacy:retention
npm run privacy:retention -- --execute
```

Без --execute ничего не удаляется. Backend minute-maintenance чистит истёкшие сессии/reset, dev-письма после 30-минутного срока ссылки и историю consent/request только для включённой страны с заданными сроками. Активные privacy/terms/offer proofs и все данные под hold исключаются из этой очистки. Тексты с реквизитами в журнале изменений legal также требуют утверждённого срока; автоматическая очистка audit/финансовых записей не включена.

## HTTPS и эквайринг

Production требует HTTPS CLIENT_URL/SERVER_URL, Secure cookie, доверенный proxy и TLS. deploy/Caddyfile.example — пример, а не действующий сертификат. SERVER_HOST по умолчанию 127.0.0.1; TRUST_PROXY задавайте только под реальную топологию. Проверяйте CORS, HSTS, CSP, отсутствие PII в reverse-proxy logs и доступ к БД.

PAYMENT_PROVIDER=sandbox работает только в development/test. Реального адаптера нет: production не стартует до интеграции. Не вводите настоящие карты в sandbox и не выдавайте его за эквайринг. Для нового провайдера реализуйте server-to-server создание с outbox/idempotency, подписанный webhook, сверку сумм/валют/заказов/статуса, реальный refund и его подтверждение, чеки/учёт. Контакты, валюты, страны и правила возврата заполните отдельно по каждой юрисдикции.

## Backup и восстановление

```powershell
# На сервере в закрытом окружении, ключ отдельно от backup:
$env:PG_DUMP_PATH = 'C:/Program Files/PostgreSQL/18/bin/pg_dump.exe'
# BACKUP_ENCRYPTION_KEY — 64 hex из криптографического генератора/хранилища секретов.
npm run db:backup
```

Не вставляйте настоящий ключ в README, Git или общий чат. Скрипт передаёт пароль pg_dump через окружение дочернего процесса, а не аргументы, шифрует custom dump AES-256-GCM и пишет server/storage/backups/*.pgdump.enc (папка в .gitignore). Формат: magic HYDRABK1 (8 bytes), IV (12), ciphertext, auth tag (16). Ключ нужен для восстановления; не теряйте его.

Проверьте размещение, ACL (в Windows mode 0600 не заменяет NTFS ACL), отдельное хранение ключей, расписание и сроки backup, шифрование дисков и monitoring ошибок. Это требует настройки владельцем. До восстановления проверяйте auth tag, расшифровывайте только в защищённую среду и тестируйте pg_restore на отдельной БД. Не перезаписывайте рабочую БД без отдельного одобрения.

Перед restore сохраните вне восстанавливаемого snapshot актуальный реестр закрытых аккаунтов, отозванных согласий и удержаний. После восстановления повторно примените прекращение доступа/обработки, очистите старые сеансы/reset и истёкшие письма; проверьте отсутствие рассылок/покупок по закрытым аккаунтам. Старый backup не должен отменять последующие решения пользователя. Отдельный реестр и процедура восстановления не настроены автоматически.

## Тесты

```powershell
npm test
npm run test:integration
npm run build
```

Integration runner использует отдельную local database *_test, создаёт её при необходимости и применяет миграции; fixtures очищаются только по созданным ID. Для удалённой среды обязательно явно задайте TEST_DATABASE_URL с суффиксом _test. Не используйте рабочую базу и не отключайте проверку имени.
